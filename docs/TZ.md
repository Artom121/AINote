# ТЗ: ИИ-ассистент для заметок и календаря

6 окт. 2026 г. · @Artem Vardanian · ред. 2 (6 окт. 2026: закрыты вопросы раздела 2, см. «Журнал изменений»)

## 1. Цель продукта

Нужно разработать многопользовательское веб-приложение: ИИ-ассистента, которым пользователь
управляет своими заметками и календарём на естественном языке, текстом или голосом.

Примеры фраз, которые ассистент должен понимать:

- «Добавь заметку: позвонить юристу насчёт договора аренды»
- «Допиши в заметку про ремонт, что плитку привезут в четверг»
- «Удали заметку про старый пароль от вайфая»
- «Что я записывал про поставщиков в сентябре?»
- «Поставь встречу с Андреем завтра в 15:00 на час»
- «Перенеси созвон с бухгалтером на пятницу»
- «Что у меня на этой неделе?»

Заметки хранятся в собственной базе приложения. Календарь синхронизируется с внешними сервисами
пользователя: в первую очередь Яндекс Календарь, затем Google Calendar. Ассистент не привязан к
встречам и не записывает созвоны: это личный секретарь по заметкам и расписанию.

## 3. Стек и архитектура

Один язык на всём проекте — TypeScript: так кодинг-агенту проще держать код согласованным.

| Слой                                       | Технология                                                        |
| ------------------------------------------ | ----------------------------------------------------------------- |
| Фронтенд + бэкенд                          | Next.js (App Router), TypeScript, Tailwind                        |
| База данных                                | PostgreSQL + расширение pgvector                                  |
| ORM и миграции                             | Drizzle ORM                                                       |
| Фоновые задачи (эмбеддинги, синхронизация) | pg-boss (очередь поверх PostgreSQL)                               |
| Авторизация                                | Auth.js (Яндекс ID; Google — Этап 5), сессии в БД                 |
| CalDAV-клиент                              | библиотека tsdav                                                  |
| LLM, эмбеддинги, распознавание речи        | через свои интерфейсы LLMProvider, EmbeddingProvider, STTProvider |
| Тесты                                      | Vitest (юнит и интеграционные), Playwright (сквозные)             |
| Развёртывание                              | Docker Compose                                                    |

Как проходит запрос «Перенеси созвон с бухгалтером на пятницу»:

1. Фронтенд отправляет сообщение в `POST /api/chat`, ответ приходит потоком.
2. Бэкенд собирает контекст: системный промпт, текущие дата и часовой пояс пользователя, последние
   20 сообщений, список инструментов.
3. LLM вызывает `list_events`, чтобы найти созвон; бэкенд выполняет инструмент через адаптер
   календаря и возвращает результат в LLM.
4. LLM вызывает `update_event`. Это действие требует подтверждения, поэтому бэкенд не выполняет
   его, а сохраняет как «ожидающее» и показывает карточку подтверждения.
5. Пользователь жмёт «Да» → `POST /api/actions/{id}/confirm` → изменение пишется в Яндекс
   Календарь, в action_log и в чат.

Структура кода:

```
src/
  app/            — страницы и API-роуты Next.js
  agent/          — цикл агента, промпты, описания инструментов
  tools/          — реализация каждого инструмента
  providers/      — llm/, embeddings/, stt/, calendar/ (адаптеры)
  db/             — схема Drizzle, миграции, запросы
  jobs/           — фоновые задачи
  lib/            — шифрование, даты и часовые пояса, утилиты
tests/            — юнит, интеграционные, e2e, eval-набор фраз
```

## 4. Пользователи и подключение аккаунтов

Каждый пользователь видит и меняет только свои данные. Это проверяется на уровне каждого запроса
к базе, а не только в интерфейсе.

Вход в приложение:

- Вход через Яндекс ID (OAuth 2.0) — основной способ, Этап 0. OAuth-токены входа не сохраняются.
- Dev-вход без OAuth для локальной разработки — доступен только при `NODE_ENV=development`.
- Вход через Google (OAuth 2.0) — Этап 5.
- Вход по email и паролю в MVP не входит.
- Сессии хранятся в БД; в настройках есть «Выйти на всех устройствах».

Подключение внешних сервисов — отдельно от входа, на странице «Интеграции». Вход через Яндекс ID
не даёт доступа к календарю: календарь подключается отдельно.

- Пользователь может подключить несколько календарей и выбрать один «по умолчанию» для новых событий
- Токены и пароли приложений хранятся зашифрованными (AES-256-GCM, ключ вне базы)
- Пользователь может отключить интеграцию; токены при этом удаляются
- Если токен протух или отозван, приложение показывает понятное сообщение и кнопку «Переподключить»

Настройки пользователя: часовой пояс (обязательно — от него зависит понимание «завтра в 15:00»;
при первом входе берётся из браузера, затем меняется в настройках), язык, календарь по умолчанию,
длительность события по умолчанию (60 минут).

## 5. Заметки

Заметка — это текст в Markdown с заголовком, тегами и историей изменений. Все операции доступны и
через ассистента, и вручную в интерфейсе.

Модель данных (минимум):

| Сущность        | Поля                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------ |
| notes           | id, user_id, title, content (Markdown), tags[], pinned, created_at, updated_at, deleted_at |
| note_versions   | id, note_id, content, title, changed_by (user / assistant), created_at                     |
| note_embeddings | note_id, chunk_index, chunk_text, embedding (pgvector)                                     |

Операции:

- Создать заметку (заголовок, если не задан, генерирует LLM — до 60 символов)
- Дописать текст в конец, заменить фрагмент, переписать заметку целиком
- Переименовать, поставить/снять теги, закрепить
- Удалить — мягко: заметка уходит в «Корзину» на 30 дней, оттуда её можно восстановить. По
  истечении срока заметку удаляет периодическая задача pg-boss (Этап 1)
- Откатить к любой предыдущей версии из истории
- Поиск: полнотекстовый (PostgreSQL tsvector, русская морфология) + семантический (по эмбеддингам)

Каждое изменение, сделанное ассистентом, создаёт новую версию в note_versions. Так любую ошибку ИИ
можно отменить одной кнопкой.

## 6. Календарь и интеграции

Все календари подключаются через единый интерфейс CalendarProvider, чтобы новый сервис добавлялся
одним классом-адаптером без изменений в агенте.

Интерфейс адаптера: `listCalendars`, `listEvents(from, to)`, `getEvent`, `createEvent`,
`updateEvent`, `deleteEvent`, `searchEvents(query, from, to)`.

| Сервис                                 | Протокол               | Авторизация                                                       | Этап   |
| -------------------------------------- | ---------------------- | ----------------------------------------------------------------- | ------ |
| Яндекс Календарь                       | CalDAV                 | Пароль приложения Яндекса; OAuth — если поддерживается для CalDAV | MVP    |
| Google Calendar                        | Google Calendar API v3 | OAuth 2.0                                                         | Этап 5 |
| Любой CalDAV (iCloud, Nextcloud и др.) | CalDAV                 | Логин + пароль приложения                                         | Этап 5 |

Требования:

- Событие: название, начало, конец, часовой пояс, описание, место, напоминание; повторяющиеся
  события — только чтение в MVP
- Чтение событий кэшируется на 5 минут; изменения сразу пишутся во внешний календарь, кэш сбрасывается
- Конфликты: перед созданием события ассистент проверяет пересечения. При пересечении показывается
  карточка подтверждения: «В это время у вас уже созвон с бухгалтером. Всё равно создать?»
- Ошибки внешнего сервиса не роняют чат: ассистент сообщает, что календарь недоступен, и
  предлагает повторить

Кодинг-агенту: перед реализацией адаптера Яндекса проверить по актуальной документации адрес
CalDAV-сервера и поддерживаемые способы авторизации.

## 7. ИИ-агент

Агент — это LLM с вызовом инструментов (tool calling). Он сам решает, какой инструмент вызвать,
но опасные действия выполняются только после подтверждения пользователя.

| Инструмент           | Что делает                                                    | Подтверждение        |
| -------------------- | ------------------------------------------------------------- | -------------------- |
| search_notes         | Полнотекстовый + семантический поиск, фильтры по дате и тегам | Нет                  |
| get_note             | Получить заметку целиком                                      | Нет                  |
| create_note          | Создать заметку                                               | Нет                  |
| update_note          | Дописать, заменить фрагмент, переписать, сменить теги         | Нет (есть откат)     |
| delete_note          | Удалить в корзину                                             | Да                   |
| list_events          | События за период                                             | Нет                  |
| create_event         | Создать событие                                               | Только при конфликте |
| update_event         | Перенести, изменить                                           | Да                   |
| delete_event         | Удалить событие                                               | Да                   |
| get_current_datetime | Текущие дата и время в часовом поясе пользователя             | Нет                  |

Правила поведения агента:

1. Если запрос неоднозначен (под «заметку про ремонт» подходят три заметки), агент показывает
   варианты и просит выбрать, а не угадывает.
2. Подтверждение показывается в интерфейсе карточкой с кнопками «Да» / «Отмена» и точным
   описанием действия.
3. Относительные даты («завтра», «в пятницу») переводятся в абсолютные по часовому поясу
   пользователя; в ответе агент всегда называет точную дату.
4. После каждого действия агент коротко сообщает, что сделал, со ссылкой на заметку или событие.
5. На вопросы («что я записывал про поставщиков?») агент отвечает только по данным пользователя и
   указывает, из каких заметок взят ответ (ссылки-цитаты). Если ничего не нашёл — так и говорит.
6. Лимит: не больше 8 вызовов инструментов на один запрос пользователя.

Подтверждение действий:

- По «Да» бэкенд сам выполняет сохранённое действие, пишет результат в чат и в action_log; LLM
  повторно не вызывается.
- Ожидающее действие живёт 15 минут, затем карточка становится неактивной.
- Если объект успел измениться (для событий — проверка по CalDAV ETag), действие не выполняется,
  пользователь видит «Событие изменилось, повторите запрос».

Поиск по заметкам (RAG): заметки режутся на фрагменты по ~500 токенов, для каждого считается
эмбеддинг и сохраняется в pgvector. Эмбеддинги пересчитываются в фоне после каждого изменения заметки.

Контекст диалога: история чата хранится в базе (chat_sessions, chat_messages, включая вызовы
инструментов). В LLM передаются последние 20 реплик пользователя и ассистента; вызовы инструментов,
относящиеся к этим репликам, передаются вместе с ними и в лимит не считаются. Пользователь может
начать новый диалог.

Слой LLM: один интерфейс LLMProvider с адаптерами (YandexGPT, OpenAI-совместимый API). Модель
выбирается через конфиг, промпты хранятся в отдельных файлах, а не в коде. В production
допускаются только модели, размещённые в РФ (см. раздел 10).

## 8. Голосовой ввод

Голос — это второй способ ввести сообщение в тот же чат, а не отдельный режим.

- Кнопка микрофона в поле ввода: нажал — говоришь, нажал ещё раз — запись остановлена (максимум 60 секунд)
- Запись в браузере через MediaRecorder, отправка на бэкенд, распознавание через Yandex SpeechKit
  (через интерфейс STTProvider, чтобы можно было заменить). При необходимости бэкенд перекодирует
  аудио через ffmpeg (Safari/iOS записывает mp4/aac)
- Распознанный текст подставляется в поле ввода; пользователь может поправить его и отправить.
  Опция в настройках: «отправлять сразу без проверки»
- Аудио после распознавания не хранится
- Озвучка ответов (TTS) не входит в MVP

## 9. Интерфейс

Три основных экрана плюс настройки. Интерфейс на русском, адаптивный: с телефона должно быть так
же удобно, как с компьютера.

1. **Чат с ассистентом** — главный экран. Лента сообщений, поле ввода с микрофоном, карточки
   подтверждения действий, ссылки на затронутые заметки и события, кнопка «Новый диалог».
2. **Заметки** — список с поиском и фильтром по тегам, редактор Markdown, история версий с кнопкой
   «Восстановить», корзина.
3. **Календарь** — вид на день и неделю, события из всех подключённых календарей, цвет по
   календарю, ручное создание и редактирование.
4. **Настройки** — профиль, часовой пояс, интеграции (подключить / переподключить / отключить),
   «Выйти на всех устройствах», удаление аккаунта.

Следом за чатом удобно видеть результат: на компьютере справа от чата — панель с заметкой или днём
календаря, которых коснулось последнее действие.

## 10. Безопасность и нефункциональные требования

Безопасность:

- Изоляция данных: каждый запрос к базе фильтруется по user_id; инструменты агента получают
  user_id из сессии, а не из ответа LLM
- Защита от prompt injection: текст заметок и событий передаётся в LLM как данные; агент не
  выполняет инструкции, найденные внутри заметок
- Токены интеграций зашифрованы, в логи не попадают ни токены, ни содержимое заметок
- HTTPS, httpOnly-куки для сессии, CSRF-защита, rate limit: 30 сообщений в минуту на пользователя
- Удаление аккаунта стирает все данные пользователя. OAuth-токены отзываются через API провайдера,
  где это возможно; пароль приложения Яндекса программно отозвать нельзя — он удаляется у нас, а
  пользователь видит подсказку отозвать его в настройках Яндекс ID
- Персональные данные граждан РФ хранятся на серверах в РФ (152-ФЗ). В production заметки, события
  и сообщения передаются только в модели, размещённые в РФ. Зарубежные модели допустимы только в
  разработке и только на тестовых данных

Нефункциональные требования:

| Параметр                                                    | Цель                                             |
| ----------------------------------------------------------- | ------------------------------------------------ |
| Первый видимый отклик ассистента (статус или начало ответа) | до 2 секунд                                      |
| Полный ответ на команду с одним инструментом                | до 8 секунд, ответ выводится потоком (streaming) |
| Поиск по заметкам                                           | до 1 секунды при 10 000 заметок у пользователя   |
| Распознавание голоса (до 15 секунд речи)                    | до 3 секунд                                      |
| Покрытие тестами бэкенда                                    | не ниже 70%                                      |

Логирование: каждый вызов инструмента агентом пишется в журнал действий (action_log: кто, что,
когда, результат) — для отладки и для показа пользователю истории действий.

## 11. Этапы и критерии приёмки

Работу делим на этапы; следующий начинается только после того, как все критерии предыдущего
выполнены и проверены.

**Этап 0. Каркас**

- [ ] Репозиторий, Docker Compose (приложение + PostgreSQL с pgvector), миграции, линтер, CI с тестами (GitHub Actions)
- [ ] Вход через Яндекс ID, сессии в БД, «выйти на всех устройствах»; dev-вход только в development; пользователь видит пустой чат

**Этап 1. Заметки без ИИ**

- [ ] CRUD заметок в интерфейсе, теги, корзина (с автоочисткой через 30 дней), история версий с откатом
- [ ] Полнотекстовый поиск по-русски находит «договор» по запросу «договоры»
- [ ] Тест: пользователь A не может получить заметку пользователя B ни через API, ни через агента

**Этап 2. Агент по заметкам**

- [ ] Все 4 примера фраз про заметки из раздела 1 выполняются правильно
- [ ] Удаление требует подтверждения; отмена ничего не меняет
- [ ] Неоднозначный запрос приводит к уточнению, а не к изменению случайной заметки
- [ ] Ответ на вопрос содержит ссылки на заметки-источники
- [ ] Набор из 30+ тестовых фраз (eval) с ожидаемыми вызовами инструментов; проходит не менее 90%
      на production-модели. Eval запускается отдельно от CI командой `pnpm eval` с настоящим ключом

**Этап 3. Яндекс Календарь**

- [ ] Подключение, просмотр событий, создание, перенос, удаление через чат и вручную
- [ ] «Завтра в 15:00» создаёт событие с верной датой в часовом поясе пользователя
- [ ] Предупреждение о пересечении событий

**Этап 4. Голос и полировка**

## 12. Правила работы для кодинг-агента

1. Работай строго по этапам из раздела 11. Закончив этап, остановись и выдай отчёт: что сделано,
   как проверить, какие критерии выполнены, что осталось.
2. Перед началом этапа составь короткий план (файлы, миграции, тесты) и только потом пиши код.
3. Не добавляй функции, которых нет в ТЗ. Если что-то в ТЗ неясно или противоречиво — задай
   вопрос, а не угадывай.
4. Каждая новая функция идёт вместе с тестами. Перед отчётом прогони все тесты и линтер; сломанные
   тесты не скрывай и не отключай.
5. Секреты (ключи API, пароли, ключ шифрования) — только через переменные окружения; добавь
   .env.example со всеми переменными без значений.
6. Внешние сервисы (LLM, SpeechKit, CalDAV) в тестах заменяй моками; для ручной проверки
   предусмотри режим с настоящими ключами. Исключение — eval-набор (`pnpm eval`), он работает с
   настоящей моделью и в CI не входит.
7. Сведения о внешних API (адреса, форматы, авторизация) проверяй по актуальной официальной
   документации, а не по памяти.
8. Веди README.md: как запустить локально, как прогнать тесты, какие переменные окружения нужны,
   как подключить Яндекс Календарь.
9. Коммиты — небольшие, на английском, в формате Conventional Commits.
